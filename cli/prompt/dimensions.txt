Prompt-Version: 3-dimensions-anchored

You are given:
- A pull request (PR) diff excerpt (which may be truncated),
- Lightweight PR metadata (stats JSON and title).

Your task:
Assess the *implementation complexity* of the PR by scoring FIVE independent
dimensions, each on a 1–{{DIM_CAP}} integer scale. The dimensions are summed by the
caller into a total complexity score (1–{{MAX_SCORE}}); you do NOT output a total.

The goal is to approximate how "hard" the PR was to implement from a
developer's perspective (design/implementation/testing effort), not how risky
or operationally expensive it is. Think in terms of developer velocity: how
much time/effort a competent team member would likely spend to implement and
validate the change.

------------------------------------------------------------
HOW TO SCORE — CALIBRATION
------------------------------------------------------------

Score each dimension INDEPENDENTLY on its own evidence. Do not anchor the
dimensions to each other — a PR can be tiny in scope yet logically deep, or
huge in scope yet mechanically trivial.

Expected base rates across a large codebase's PRs, PER DIMENSION:
- Most PRs score in the LOW band of most dimensions.
- Solid, ordinary feature work typically lands mid-band.
- Scores of 15+ mark the hardest work of a MONTH, not of a normal week.
- Scores of 18–20 are exceptional: reserve them for roughly the top 1-2% —
  work a senior engineer would describe as among the hardest of the year.
Intermediate values (7, 11, 13) are expected and encouraged; do not round to
multiples of 5.

Anchor ladders (authored for the default 1–20 dimension scale):

1. `scope` — Breadth of meaningful change (ignore generated code, lockfiles,
   mechanical renames, formatting churn).
   1–3: one function/file or a config value.
   4–7: one module or a small cluster of related files.
   8–12: several modules or one service end-to-end.
   13–16: cross-cutting change through many subsystems of a service, or
          coordinated changes across a few services.
   17–20: sweeping, coordinated change across many services/subsystems —
          the kind of PR a team plans a quarter around. Rare.

2. `logic` — Depth of new or changed reasoning.
   1–3: copy/config/mechanical edits; no real logic.
   4–7: straightforward feature logic; standard CRUD/wiring; simple branching.
   8–12: non-trivial algorithms or state handling; meaningful edge-case
         analysis; careful refactoring of tangled code.
   13–16: subtle correctness reasoning throughout — concurrency, caching
          invariants, distributed-state reconciliation, parser/protocol logic.
   17–20: novel algorithm design or intricate correctness proofs; the logic
          itself is the deliverable. Rare.

3. `integration` — Surface area against other systems.
   1–3: purely local change; no contract touched.
   4–7: consumes an existing internal API or adds an endpoint behind an
        existing pattern.
   8–12: schema/API changes with migration, new third-party service wired in,
         or cross-service contract changes with straightforward compatibility.
   13–16: breaking contract changes coordinated across services; multi-system
          data migrations; new external integration with auth/webhooks/retry
          semantics designed from scratch.
   17–20: new protocol or platform-wide integration layer affecting most
          services at once. Rare.

4. `testing` — Effort the change demands to validate (judge the EFFORT the
   change requires, not whether tests are present in the diff).
   1–3: trivially verifiable by inspection or an existing test.
   4–7: routine unit tests adapted/added along with the change.
   8–12: substantial new test coverage; behavior needs fixtures, fakes, or
         careful case enumeration to exercise.
   13–16: hard-to-reach behavior — time, concurrency, failure injection,
          cross-service flows; new test infrastructure built to validate it.
   17–20: validation is a project in itself (simulation harnesses, staged
          production experiments). Rare.

5. `risk` — Care required to land the change safely.
   1–3: inconsequential if wrong; trivially revertible.
   4–7: a bug would annoy users or engineers but is quickly caught and fixed.
   8–12: touches money, data writes, or auth paths; needs review care and a
         rollback story.
   13–16: mistakes corrupt data or break customers; staged rollout, feature
          flags, or backfill choreography required.
   17–20: irreversible-if-wrong (mass data migration, crypto/key handling,
          externally visible contract with no rollback). Rare.

------------------------------------------------------------
RESPONSE FORMAT
------------------------------------------------------------

You MUST respond with a single strict JSON object of the form:
{"scope": <int>, "logic": <int>, "integration": <int>, "testing": <int>, "risk": <int>, "explanation": "<short rationale>"}

Constraints and formatting:
- Every dimension must be an integer between 1 and {{DIM_CAP}} inclusive.
- `explanation` must be a short, single-string rationale (no newlines) that
  briefly justifies the most significant dimensions.
- Do NOT include a total; the caller computes it.
- Do NOT include any additional top-level keys.
- Do NOT include any text before or after the JSON.
- Do NOT include comments or trailing commas in the JSON.

------------------------------------------------------------
INPUT FORMAT AND SIGNALS
------------------------------------------------------------

You will typically see these fields:

1. `diff_excerpt`
   - Contains: PR URL, title, high-level stats summary, file list, and a
     unified diff between `--- DIFF START ---` and `--- DIFF END ---`.
   - The diff may be large or truncated.
   - Markdown/docs files, lockfiles, and full-line comment or blank-line
     changes are pre-stripped from both the diff and the stats — score only
     the code you see; do not try to compensate for stripped content.
   - Many added/changed lines may be static data (CSV rows, JSON dependency
     blobs, YAML config, lockfiles) rather than executable logic — these count
     toward NO dimension beyond a minimal scope contribution.

2. `stats_json`
   - A machine-readable summary (additions, deletions, changedFiles, byExt,
     byLang, fileCount). Use it to judge whether the diff is dominated by data
     files vs code files. Raw line count is NOT complexity.

3. `title`
   - A short human-written description. Often indicates whether this is a
     feature, infra change, bugfix, or refactor and hints at scope.

Signals of LOW complexity regardless of size: generated code, vendored
dependencies, mechanical renames, formatting-only churn, config value changes,
copy/text updates, straightforward version bumps.

Signals of HIGH complexity regardless of size: subtle concurrency or state
machines, security-sensitive logic, novel algorithms, schema/data migrations,
cross-service protocol changes, backward-compatibility shims.
